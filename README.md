# Text-to-Cube on BIRD: prompt-engineering harness vs LoRA fine-tuning

**CE893 Generative AI, MSc project.** A small open-weight LLM running on one consumer GPU answers
plain-English questions about a database. It does not write SQL: it writes queries for
[Cube](https://cube.dev), a *semantic layer* that sits on the database and exposes named measures and
dimensions. The question the project answers is:

> With the same agent, tools and prompt, how much does a **LoRA adapter** add over **prompt engineering alone**,
> and can the adapter take over part of the prompt so that each question costs fewer tokens?

## The project in one picture

```
 question ──► ADK agent (Qwen2.5-Coder 7B or 14B, served by Ollama)
                 │  system prompt: query guide + the database's Cube schema
                 │  tools: search_values ─ find exact stored values ("Lewis Hamilton")
                 │         run_query     ─ try a draft query, see rows or Cube's error
                 │         submit_answer ─ hand in the final Cube query
                 ▼
            Cube semantic layer on DuckDB (BIRD databases)
                 ▼
 answer rows ──► compared with the result of BIRD's gold SQL  (execution accuracy)
                 ▼
            demo app: A2UI surface with a Highcharts chart, table, query and tool trace
```

**Technologies required by the module brief and where they are used:**

- **Cube.js**: the semantic layer the model queries (`cube/`, models generated by `scripts/gen_cube_models.py`).
- **ADK** (Google Agent Development Kit): the agent loop that calls the model and the tools (`harness/agent.py`).
  ADK talks to the local model through LiteLLM, so any Ollama or OpenAI-compatible server works.
- **Highcharts** and **[A2UI](https://github.com/a2ui-project/a2ui)**: the demo app turns each answer into A2UI
  messages with a Highcharts chart component (`app/presenter.py`, `app/web/`).

## Data

All data is from the [BIRD](https://bird-bench.github.io/) text-to-SQL benchmark (CC BY-SA 4.0). No database
appears in more than one split.

| Split | BIRD source | Size | Use |
|---|---|---|---|
| Test | dev set, databases `formula_1` and `student_club` | 332 questions (`splits/test_ids.json`) | frozen before any experiment; every result below |
| Harness tuning | dev set, `superhero`, `toxicology`, `california_schools` | 363 questions | developing the prompt and tools (never the test set) |
| LoRA training | train set, 58 databases (55 train + 3 validation) | 3,531 question → Cube query pairs (`training_data/`) | fine-tuning |

The training pairs were made by translating BIRD's gold SQL into Cube queries with a rule-based translator
(`harness/sql2cube.py`) and **keeping only pairs whose Cube result equals the SQL result** (3,531 of 8,003).
Each pair was then written as a full agent transcript (prompt, tool calls, tool replies, answer), so the model
learns the harness's exact format.

BIRD gives each question an *evidence hint* (for example "full name refers to forename, surname"). A real user
would not type that, so **all reported results hide the hint from the model** (`--no-evidence`).

## Compared systems

Every system uses the **same harness** (agent, tools and checks, version v4.2, frozen before fine-tuning) and
the same Qwen2.5-Coder model file, 4-bit (Q4_K_M) in Ollama. The names give the adapter and the prompt it
was trained and run with; they match the report.

| System | What changes |
|---|---|
| **harness only** (baseline) | base model, full prompt: query guide, tool schemas, full database schema |
| **LoRA, full prompt** (proposed) | the same model plus a LoRA adapter trained on the 3,531 transcripts; same prompt |
| **LoRA, lean prompt** | adapter trained and run with a short prompt: no query guide, no tool schemas, compact schema |
| **noschema LoRA, no schema / lean prompt** | adapter also trained on synthetic questions about the two test schemas, run without any schema, or with the lean prompt |
| **lookup LoRA, full / lean prompt** (extra arms) | adapters retrained so they look filter values up with `search_values` (more lookup examples, trained `<tool_call>` tokens) |

Each was run at two sizes, Qwen2.5-Coder **7B** and **14B** Instruct.

## Results

332 test questions, no hint. **Strict** execution accuracy is the headline metric: the rows must equal the
gold SQL's rows (column order ignored). *Relaxed* also accepts extra columns, which Cube must return when it
sorts by a field. Prompt tokens are summed over all model calls of a question. *p*: exact McNemar test on
strict accuracy against the harness-only system of the same size. (Report Table 5; the noschema rows are in
the report's Fig. 8.)

| System | 7B strict | 7B relaxed | 7B prompt tok./q | 14B strict | 14B relaxed | 14B prompt tok./q |
|---|---|---|---|---|---|---|
| harness only | 21.4 | 27.7 | 15,929 | 27.4 | 35.8 | 11,952 |
| LoRA, full prompt | **36.7** (p = 5e-8) | 40.7 | 7,672 | **40.7** (p = 2e-7) | 45.5 | 7,344 |
| LoRA, lean prompt | 34.6 | 36.7 | 3,242 | 40.1 | 46.1 | 2,988 |
| noschema LoRA, no schema | 18.1 | 19.9 | 1,616 | 24.7 | 25.6 | 1,140 |
| noschema LoRA, lean prompt | 37.0 | 39.2 | 3,201 | 41.0 | 45.5 | 2,929 |
| lookup LoRA, full prompt | **41.9** | 47.6 | 12,204 | 44.9 | 48.8 | 11,638 |
| lookup LoRA, lean prompt | 33.4 | 37.3 | 5,813 | **46.1** | 52.1 | 4,728 |

What this shows:

1. **The LoRA adds 13 to 15 points** over prompt engineering at both sizes, and the fine-tuned 7B beats the
   14B harness-only model. It also halves the model calls and the latency per question.
2. **Most of the prompt can move into the weights, but not the schema.** The lean-prompt LoRA stays within
   about 2 points of the full-prompt LoRA (not significant) at about 40% of the prompt tokens. Without any
   schema the model invents field names and accuracy falls by 16 to 19 points. A full-prompt adapter given the
   lean prompt without retraining scores 0%: an adapter only works with the prompt it was trained on.
3. **Teaching the adapter to look values up helps further** (extra arms): +5.2 points at 7B and +4.2 at 14B
   over the original LoRA. The best result is the 14B lookup LoRA with the lean prompt, 46.1% at 4.7k prompt
   tokens per question. The 7B lookup LoRA with the lean prompt loops between lookups and drafts, so it does
   not improve (kept as a negative result).

The test set is small (332 questions), so the report gives a paired significance test for each comparison.

## Reproducing the results

### 1. From the stored results (no GPU, about a minute)

Everything in the report is computed from `results/`:

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install pandas sqlglot scipy matplotlib jupyter
jupyter notebook notebook/CE893_walkthrough.ipynb      # or open it in VS Code and Run All
```

Both notebooks are committed with their outputs, so it can be read on GitHub without running it.

### 2. Running the systems again (needs a GPU)

Needs Python 3.11+, Node.js 20+, [Ollama](https://ollama.com) and, for training, a 16 GB NVIDIA GPU
(we used an RTX 5070 Ti). One 332-question evaluation takes 10 to 25 minutes; training takes about 5 hours (7B)
or 9 hours (14B).

```bash
pip install -r requirements.txt
python scripts/download_bird.py
python scripts/build_duckdb.py --bird-dir data/bird --out data/bird.duckdb --db formula_1 --db student_club
python scripts/gen_cube_models.py --bird-dir data/bird --out cube/model --db formula_1 --db student_club
cd cube && cp .env.example .env && npm install && npm run dev        # Cube on :4000 (Windows: copy)
```

In a second terminal, the baseline (harness only, 7B):

```bash
ollama pull qwen2.5-coder:7b
python -m pytest tests -q                                              # sanity check
python -m harness.evaluate --db formula_1 --db student_club --ids-file splits/test_ids.json --no-evidence \
    --model ollama_chat/qwen2.5-coder:7b --setup harness-v4.2-7b-nohint --out runs/test_nohint_harness_7b.jsonl
```

The LoRA system (7B; for 14B use the 14B model names and `--max-len 4096`):

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu128 && pip install -r requirements-train.txt
python scripts/make_sft.py --data training_data --out data/sft
python scripts/train_lora.py --base Qwen/Qwen2.5-Coder-7B-Instruct --out lora/qwen7b
python scripts/export_ollama.py --base Qwen/Qwen2.5-Coder-7B-Instruct --adapter lora/qwen7b/final \
    --llama-cpp ../llama.cpp --quantize ../llama.cpp/build/bin/llama-quantize --ollama-base qwen2.5-coder:7b --name qwen7b-cube-lora
python -m harness.evaluate --db formula_1 --db student_club --ids-file splits/test_ids.json --no-evidence \
    --model ollama_chat/qwen7b-cube-lora --setup lora-v4.2-7b-nohint --out runs/test_nohint_lora_7b.jsonl
```

Each output line holds the question, the predicted Cube query, strict and relaxed correctness, steps, tokens,
latency and the full tool trace. Copy a finished run, gzipped, into `results/runs/` under the name used in
`report/analysis.py` and re-run the notebook. The commands for the other systems (lean, noschema, lookup) are in
[`docs/README_technical.md`](docs/README_technical.md) and in the last section of the notebook.

### 3. The demo app

With Cube on :4000 and the models in Ollama (models that are not installed are shown as such):

```bash
cd app/web && npm install && npm run build && cd ../..
python -m app.server                    # open http://localhost:8000
```

Pick a system (or compare several side by side), ask a question, and the answer appears as a chart with tabs for
the table, the Cube query and the agent's tool calls.

## Limitations

Two test databases and one model family (Qwen2.5-Coder), 4-bit weights, and a semantic layer that cannot express
about 30% of BIRD's gold SQL (nested queries, CASE arithmetic, string slicing), which caps every system. The
report's Limitations section discusses these and the threats to validity.
